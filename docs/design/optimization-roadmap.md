## 一、这份路线图回答什么

评审的结语给出了很好的诊断，但**诊断不是排期**。它说"如果只能做三件事"，没有回答：

- 这三年事之间有依赖吗？先做哪个？
- 每件事的"做完"如何被机器验证？
- 哪些事卡在用户授权 / 外部环境上，必须显式等待而不是假装能排期？
- 哪件事必须等一个产品决策（而不是工程努力）才能开工？

本路线图把评审的 22 个问题条目 + 8 条架构风险**全部**落到 7 期里，每一期给出目标、具体改动点（文件级）、验收标准（可执行命令级）、阻塞与前置、以及明确的**不做清单**。

一句话概括分期逻辑：

> **先把红色基线变绿（第 0 期）→ 再把三个对外承诺的证据补齐（第 1 期）→ 再让外面的人装得上、看得懂（第 2 期）→ 再补编辑器的诚意底线（第 3 期）→ 再让交付物在别人的 PPT 里合格（第 4 期）→ 再打开被自设红线压住的产品价值（第 5 期）→ 最后清掉会持续复利的技术债与做生态（第 6 期）。**

4. **反馈环**：`--only themes` 等分组可独立执行；典型分组耗时显著低于全量（给出实测数字）。并行化后全量结果集与串行一致。
5. **规则审计表**：每条【默认】规则有明确去向（升 lint / 保留并说明 / 删除）；回访【硬规则】标签统一率 100%（无未打标签的硬规则）；首轮过闸率有历史曲线（至少 3 个数据点）。
6. **社区管道**：模拟一次外部投稿——按 `CONTRIBUTING-THEME.md` 提交一个主题，从 Schema 校验 → 两两 diff → 感知评审 → 入库全流程走通并留痕。
7. **数据入口**：给定一个 CSV，生成含图表的 deck 并过双闸；编辑器中改一个图表数值，几何随之变化且保存幂等。
8. **画幅常数**：全仓库 1920×1080 类常数集中在单一配置源（`grep` 可证散落处为 0）。

**不做**：不实现竖版/方版画幅（只收敛常数，G-9 明确"不急于实现"）；不引入框架或构建期依赖到交付物（构建只作用于开发侧单文件拼接）。

**规模**：6.1/6.2/6.4 为 S–M；6.3 为 **L**；6.5/6.6/6.7/6.8 为 M。

## 六、需要用户拍板的产品决策岔口

以下不是工程问题，**必须由用户决定**；在决策前对应的实现不得擅自开工（评审建议 ≠ 已决策）。

**① 是否解禁"背景升维"第三态（P-3 / R8）**
现状是用户 2026-09-21 明确否决的硬规则（`page-render-mode.md:4,13`：整页生图只保留完整烙入一种形态）。评审认为这是"性价比最高的一个产品决策翻案"，理由是它同时拥有图像级视觉上限 + 文字零错字 + 保持可编辑。
**决策项**：二态改为三态（纯 HTML / 背景升维 / 整页烙入）。若同意，第 5 期 5.1 解锁并可提前与第 3 期并行；若维持原判，第 5 期只做 5.2–5.5，且 B-3 的文字风险继续靠"事后重 roll"止损（应在文档里如实写明这是已知代价）。

**② `await_intent` 是否增加短轮询档位（M-1 / R4）**
评审建议加"短轮询 + 技能侧剧本"作为低超时宿主的兼容回退；但项目自己的 `1013_mcp_await_intent_timeout.md:17` 已明确**否决**了短轮询与工作流降级两条方向，理由是"每回合一次 `await_intent(3600)`"的语义在修复后成立。
**决策项**：以哪一份结论为准。建议做法是——先做 1.6(a) 的 stdin EOF 自退防御并重跑 Kimi，用**实测**决定是否需要兼容档位，而不是用文档裁决文档。

**③ 英文化的产品边界（G-1）**
全量英文化（SKILL + 11 references + 29 主题 + 编辑器 i18n）是数周的投入，且需要人审。
**决策项**：是"全量英文化"还是"英文 README + 英文 SKILL 主干 + 英文 demo"的最小传播集（后者成本约为前者的 1/3）。这决定第 2 期 2.5 的范围。

**④ 真实付费生图的预算与授权（B-1）**
评审建议"申请一次小额预算跑通 3 页代表场景"。这需要用户显式授权付费调用。
**决策项**：授权额度与场景选择（建议沿用评审的三场景：封面巨字 / 数据英雄 / 图文证据）。未授权前，1.3 只能停在"脚本就绪 + 台账模板就绪"，状态维持 UNKNOWN。

## 七、全局纪律与本路线图明确不做的事

**纪律（沿用并强化项目既有红线）**

1. **证据分级**：`BLOCKED` / `UNKNOWN` / `NOT_RUN` 永远不得写成 PASS；「部分验证」必须写明验证了哪一部分、哪一部分没有。
2. **契约先行**：凡涉及编辑器与生成器之间的约定，先改 `editing-contract.md` 再改两侧（第 3、5、6 期的多项都遵守此序）。
3. **每期必须有可执行验收**：没有机器可跑或可复核的验收标准的条目，不进排期。
4. **文档与实际同步是红线**：第 0 期之后，"文档数字 ≠ 实物"应被视为缺陷而非小事。
5. **不复刻范例、不夸大宣传**：README/宣传语必须与能力证据同步（第 1、4 期各自负责自己那部分表述的校准）。

**本路线图明确不做**（防止无边界扩张）

- 不做编辑器自由布局（拖动/resize/z-index/新增文本框）——产品哲学已定：AI 构图、人删减纠错替换。
- 不做页面内 AI 调用——AI 位置固定在开发侧。
- 不做协同编辑、不做云端服务、不做公网暴露（M-3 只做到"可达 URL"的诚实说明与 `--bind`，不做反向代理方案）。
- 不把交付物变成需要构建的产物——所有构建/模块化只作用于开发侧。
- 不在没有真实渲染验证的前提下把 PPTX 可编辑性宣传为"已验证"。
- 不为"主题数量"而批量造主题——主题库的增长走社区管道（第 6 期），并把入库门槛 + 感知评审一起交给社区。

## 八、一句话总结

评审的诊断是对的：**这个项目不缺"再深一层的正确性"，缺的是把已有正确性兑换成外部世界可感知的价值。**

这份路线图据此把价值兑换拆成有序的四段——**先诚实（第 0 期）、再有证据（第 1 期）、再被够得着（第 2 期）、再被用得爽（第 3–4 期）**，然后才是打开视觉上限（第 5 期）与清债做生态（第 6 期）。其中第 1 期的三个验证和第 2 期的一条命令安装，是投入产出比最高的两期；第 5.1 的背景升维是收益最大但**必须由用户先拍板**的一项。
