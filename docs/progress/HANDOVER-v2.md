## 3. 批次 1 v2 经验教训（避免二次犯错）

### 3.1 v1 的 28 条问题分类（`phase6-batch1-issues.md`）

批次 1 v1（E6/G2/E7/F1）经过 rev2–rev9 多轮反复优化后被判定「完全不可用」，根因分 6 类：

1. **方法论根问题**：执行模型无法查看渲染图，视觉判断依赖量化指标 + 用户目视；优化缺少总纲，打地鼠式修补；度量信号与设计意图冲突。
2. **内容对比不对等**：曾用拆散的 KPI 页对比旧完整页。
3. **逐主题未解决问题**：E6 卡片凌乱/特色丢失；G2 字号偏小；E7 页型雷同/空白过高；F1 重心失衡/玻璃太透明。
4. **设计要素层**：正文用 caption 而非正文级；KPI 字号不统一；边框/阴影零散；padding 手动硬排。
5. **差异化维度矛盾**：方向维度太窄必撞车；明度反转被指纹极性归一抹平；「要特色」与「灰度可分」冲突。
6. **契约工程**：布局改动未回写 theme.md；审计误报 `var(--t-*)` 为裸写。

### 3.2 v2 的修复路径与最终状态

v2 重启后采取的优化策略（最终 4 套通过验收）：

| 步骤 | 做了什么 | 效果 |
|---|---|---|
| **G10 契约重写** | 每套补全 7 字段 + type_scale px@1920 + signature_operator | 主题获得构图主权 |
| **signature_operator 驱动 DOM** | 不是换 token 换皮，而是按算子重编译 DOM | 灰度去色后仍可辨 |
| **页面容量纪律** | typography.md §4.1 新增留白率上下限 + 9 宫格空间分布均衡性 | 消除 F1「玻璃孤零零」/ G2「重心偏移」 |
| **容器组一致性** | components.md §13 新增同组同宽/同高/同圆角/同描边 | 消除 KPI 容器参差不齐 |
| **标题 flush 检测** | Range API 测实际文本渲染宽度 vs 容器内宽（>97% 警告） | 消除 E6 标题溢出 |
| **字号下限** | E6/C1 的 `:root` 追加 `--t-caption:20px; --t-meta:18px` | 消除黑场/糖果底小字不可读 |
| **标题不换行原则** | 用户明确：「标题一般都不会换行，所以是按照容器调整字号」 | 按容器宽度调 `--t-display` 而非让标题折行 |

### 3.4 ⚠️ 必须避免的 12 个二次犯错

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | **并行 dispatch 子 agent 超过 2 个** | TPM 限制下 4 个并行 agent 必定 429。**最多并行 2 个**，或串行 dispatch |
| 2 | **标题让换行** | 用户明确：「标题一般都不会换行，所以是按照容器调整字号」——调 `--t-display` 而非折行 |
| 3 | **只查画布越界不查容器内溢出** | 补「最近显式 `top`+`height` 绝对定位祖先」检测（C3「361家」曾漏检） |
| 4 | **重叠检测不排除旋转元素** | 排除带 `transform` 的元素（E5 −12° 力带 AABB 虚胖假阳性） |
| 5 | **同组 KPI 用等宽检测** | 不同字数 KPI 数字自然宽度不同；改检测 x 间距规则性（gap < 0 即错位） |
| 6 | **titleFlush 用 bounding box 宽度** | 块级 div 填满 100% 容器宽度必误报；用 Range API 测实际文本渲染宽度 |
| 7 | **留白只查下限不查上限** | 低密度 ≥40% 但上限 ≤65%；高密度 ≥20% 但上限 ≤50%。F1 玻璃孤零零 = 留白超上限 |
| 8 | **只查留白率不查 9 宫格** | G2 全部 KPI 在右侧、左侧空空——留白率合格但 9 宫格有空格。3×3 网格无空格 |
| 9 | **布局改动不回写 theme.md** | G10 invariants 必须与实际产物一致；改了布局必须同步改契约 |
| 10 | **审计把 `var(--t-*)` 计作裸写字号** | `font-size:var(--t-display)` 不是裸写；只查裸写 inline px |
| 11 | **`git add -A`** | `.workbuddy/`、`SlideForge.zip`、h1 demo 图仍未被 gitignore 忽略；用 `git add -u` + 显式路径 |
| 12 | **同一消息对同一文件发多个 Edit** | 会竞态丢一个 → 一次只改一处 |

### 3.5 本机环境坑（沿用 v1 §6）

| 项 | 值 |
|---|---|
| shell shim 缺失 | `dirname`/`head`/`tail`/`ls`/`mkdir`/`cat`/`sed` 不可用或静默失败 → 用托管 Node `fs`/`child_process.execFileSync`，不接管道 |
| 同文件多 Edit | 一条消息里对同一文件发多个 Edit 会竞态丢一个 → 一次只改一处 |
| Playwright | 托管 Node + `playwright-core@1.65.0`（`~/.workbuddy/binaries/node/workspace/node_modules`）+ 系统 Chrome（`C:/Program Files/Google/Chrome/Application/chrome.exe`），用 `executablePath` 复用 |
| stdout 被吞 | 重定向到 `.log` 再用 Node 读 |

## 5. 分批优化与验收 SOP（v2 更新）

### 5.1 铁律

1. **每批恰好 4 套**（尾批可 3 套），不多做。
2. **同一批内必须用同一份内容对象**做基线，保证 A/B 公平。
3. **多类数据压力测试**必须跑，不能只渲一页。
4. **自动化只举证，不代替验收**：审计全绿 ≠ 通过；必须出 A/B 与验收包，**停下等用户明确「通过」**。
5. 用户打回时，只重做该批，**不带着问题进下一批**。
6. 每批的变更与报告落到 `docs/progress/`，提交本地；**不要主动 push**。
7. **子 agent 最多并行 2 个**（TPM 限制），或串行 dispatch。

### 5.2 批次表（v2 重排）

| 批次 | 4 套主题 | 重点 |
|---|---|---|
| **3** | G4 靛墨黄页 / G5 三色旬刊 / E2 蓝图 / E3 装饰艺术 | 色法 ×2 + 线法 + 空间；G4/G5 是色法轴最后两套，须与 E6/G2 逼出结构级分化；E2 蓝图的标注引线 + E3 装饰艺术的几何对称是签名算子 |
| **4** | C2 暗夜植物园 / C4 纸与墨 / D1 奶油物语 / D3 手绘油彩 | 质感轴聚批；G3 背景配给制与 texture-on 逐页落码 |

### 5.3 每批标准作业流程（Step 0–8）

| Step | 动作 | 产出 |
|---|---|---|
| **0 冻结基线** | 固定本批 4 套 + 同一内容对象；记录各套旧图作 A/B 对照 | `brief.md` |
| **1 写 G10 契约** | 每套补全 7 字段 + type_scale px@1920 + DOM 结构测试 | 4 份 `theme.md` |
| **2 令牌与母题** | `--t-*` 令牌源 + G9 `:root` 注入 + `.mt-*` 命名空间唯一 | 4 份 `theme.md` |
| **3 构造测试集** | 6 页型 × 4 主题 = 24 页基线 + 16 页压力集（≥40 页/批） | `build.js` + `sampler.html` |
| **4 编译** | 按各套 `signature_operator` **重编译 DOM**（不是换 token）；字号只用 `.t-*` 角色类 | `sampler.html` |
| **5 自动审计** | Playwright 逐 section 截图 1920×1080 + 逐节点 bbox / computed style；**12 项**阈值 | `report.json` + PNG |
| **6 指纹与盲测** | `_fingerprint.py` 量类间/类内相关 + 去色 240×135 缩略图盲测 | 指纹 JSON + `blind-test.html` |
| **7 出验收包并停** | 新旧 A/B 并排 + 本批报告；**present 给用户，明确请求验收** | `report.md`、`compare.html` |
| **8 验收 PPTX** | 用户通过后，用技能生成 5 页不同密度 PPTX 做最终验收 | `tests/decks/acceptance/<theme>/index.html` |

### 5.4 自动验收阈值（v2：12 项，v1 的 9 项 + 3 项新增）

| 项 | 阈值 | 工具/注意 |
|---|---|---|
| 画布越界 | 0 | `run.js`：文本 bbox vs 1920×1080 |
| **容器内溢出** | 0 | 最近显式 `top`+`height` 绝对定位祖先检测 |
| 弱读 | 0 | 字号 ≥18px 且 `opacity < 0.9` |
| 同层文本块重叠 | 0 | **排除带 `transform` 的元素** |
| pageErrors | 0 | Playwright |
| 裸写 inline `font-size` | 0 | `var(--t-*)` 不算裸写 |
| 字号地板 | 全部 ≥ 角色 floor | computed style |

### 5.7 验收 PPTX 制作（v2 新增 Step 8）

用户通过 G10 契约 + sampler 验收后，需制作 5 页不同内容/密度的 HTML deck 做最终验收：

| 页 | 叙事角色 | 密度 | 内容概述 |
|---|---|---|---|
| 1 | 封面 | 低密度 | 品牌名 + 主题 + 日期 |
| 2 | 数据宣言 | 高密度 | 3-4 项核心 KPI + 说明 |
| 3 | 分析 | 高密度 | 3 段分析 + 关键词 |
| 4 | 声明/Claim | 低密度 | 一句主张 + 说明 |
| 5 | 收束 | 低密度 | 口号 + 联系方式 |

**执行方式**：
- ⚠️ **不要并行 dispatch 4+ 个子 agent**（TPM 限制会导致 429 全部失败）
- 推荐方式 1：串行 dispatch，一个 agent 做完再 dispatch 下一个
- 推荐方式 2：自己直接生成（读取 skeleton + theme.md，手动填充 SLOT 槽位）
- 输出路径：`tests/decks/acceptance/<theme-id>/index.html`
- 生成后需跑渲染校验（`check-render.py`）+ 容量门禁（`check-capacity.py`）

> **本次已生成的 4 份 HTML**（`tests/decks/acceptance/{e6,g2,f1,c1}/index.html`）是子 agent 在 429 前产出的，**需新 session 渲染校验后确认是否可用**。每份约 1200-1400 行，5 页 slides。
