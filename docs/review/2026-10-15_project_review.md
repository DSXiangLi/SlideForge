## 总评

这是工程纪律极严苛的 AI PPT 项目。它在三个维度上显著领先同类（gamma / tome /
各家 ppt-skill）：

1. **"HTML 为中介"的三形态架构**在理论上是正确答案：向上烙入生图、向下导出 PPTX、
   中间层可编辑，content-hash 串联 stale 检测——解决了 AI PPT 的根本痛点
   "改一个字重掷全部骰子"。
2. **双闸共用同一数学**（check-capacity 预认证 ≡ certify-pptx 出厂认证）是全行业
   罕见的工程洞察——"生成侧过闸则导出第一轮认证净"把 HTML→PPTX 的漂移问题从
   "事后修"变成"事前防"。
3. **Bridge 的一致性设计**（SQLite/WAL 真相、attempt 隔离、revision CAS、
   publication journal、owner 持久化）达到了分布式系统的严谨度，"AI 不可能弄坏
   你的文件"确实被架构保证了。

但它同时也是一个**复杂度已经触顶、而真实世界验证严重不足**的项目。核心矛盾一句话：
**项目把 95% 的工程力量花在"内部正确性"上，而决定它能否爆火的是"外部可达性"——
后者目前几乎是零。**

## 一、设计理念

### 做对的

- **五条第一性原则是真原则，不是口号**。"决策前置"（主题库只选不改）、"容量先于
  版式"、"文件即真相"每一条都能追溯到具体的失败模式，且落到了可验证的机制上
  （主题 Schema 校验器、check-capacity、editing-contract）。
- **"范例是矿不是图"的协作约定**（量化解剖 → 范式条款 → 验收资产）是极少见的
  方法论自觉，`docs/research/` 下 10 个竞品解剖报告证明不是空话。
- **规则三级效力制**（硬规则/默认/参考）解决了 skill 文档的普遍问题——所有规则
  等权导致 agent 全都不执行。

### 问题

#### P-1【理念级】规则密度已经超过 agent 的指令遵循能力上限

SKILL.md 400 行 + 11 个 references 按需加载，但一次完整生成要加载的规则量
（SKILL + briefing + themes index + theme.md + typography + components + motion +
editing-contract）保守估计 3–5 万 token，其中硬规则超过 60 条。LLM 的指令遵循率随
规则数量**超线性衰减**——这意味着项目实际依赖的是"校验器兜底"而不是"agent 遵守"。
这个事实本身没问题（校验器确实在兜底），但有两个后果没被正视：

- **非硬规则（【默认】/【参考】级）在实践中约等于不存在**——它们没有校验器，
  agent 会系统性丢弃。建议：审计所有【默认】规则，要么升级成 lint（如"连续两页
  构图雷同即失败"完全可以写成基于 manifest 的结构相似度检查），要么降级删除，
  省出指令预算。
- **修复成本**：agent 违反硬规则 → 校验器拦截 → agent 重试，每一轮都是完整生成
  成本。应统计"首轮过闸率"作为技能的核心健康指标（目前验收只记录最终 PASS，
  不记录重试次数）。

#### P-2【理念级】"主题只选不改"与企业场景的根本冲突没有解

"保护审美比给自由更重要"对个人用户成立，但**企业用户的第一需求是品牌 VI 合规**——
logo、品牌色、指定字体是刚需不是偏好。目前的答案（briefing.md："品牌红 #X → e8
号外红变体"的最近邻映射）在真实企业场景会被直接否决。这是通往商业化/爆火路上
最大的一块缺失。解法见 §七 G-5（品牌适配层）。

#### P-3【理念级】"不存在混合态"（烙入禁止背景生图 + HTML 文字叠加）值得重新辩论

`page-render-mode.md` 把烙入定义为全有全无：整页烧死或纯 HTML。这保住了架构
纯洁性，但牺牲了最有价值的中间形态——**AI 生成背景/氛围层 + HTML 文字层叠加**，
它同时拥有：

- 图像级视觉上限；
- 文字零错字风险（bake 最大的失败模式就是文字渲染，bake-prompts.md 自己承认
  "每个要渲染的字都是错字风险敞口"、905 字符即系统性截断）；
- 保持可编辑。

技术上它只是一个带 `data-image-slot="page-bg-16x9"` 的满幅底图 + 现有文字层，
契约几乎零扩展。竞品（gamma 的 AI 背景、canva 的 magic design）全部走这条路线。
当初禁止它的理由（文字与画面光影无法融合、层级关系模糊）可以理解，但"烙入 = 升维"
语义确立后（v3/v4），这个禁令应该重新评估为**三态**：纯 HTML / 背景升维（文字保活）/
整页烙入（文字烧死）。这可能是性价比最高的一个产品决策翻案。

## 二、设计实现

### 做对的

- 编辑器 srcdoc iframe 隔离 + Shadow DOM 缩略图 + 保存前净化 + 两段编辑手势，
  细节处理成熟（甚至处理了"3D 合成改变 iframe 栅格化路径导致文字抗锯齿变化"
  这种级别的坑）。
- 保存三通道降级链（Bridge → /api/save → FSAA → 下载）+ 嵌入态强制 postMessage
  的判断正确。
- `docs/learnings/` 踩坑台账 + "测试不能只用 reduced-motion"这类血泪规则说明
  回归体系真的在工作。

### 问题

#### I-1【高危】骨架版本漂移没有升级通道

skeleton.html（68KB 框架层 CSS/JS）被**逐字复制进每一个产出 deck**，目前已到
v7.6。这意味着：

- 已交付的 v7.0 deck 永远停在 v7.0 的框架 bug 上；
- 编辑器要兼容所有历史骨架版本的净化清单/动效归位规则（契约 v5–v8.1 并存）；
- 骨架每出一个 bug（如最近的 `getElementById` null 崩溃导致白屏），所有存量 deck
  都带着这个 bug 无法批量修复。

**建议**：写一个 `scripts/upgrade-skeleton.py`——框架层是"禁止修改区"恰恰意味着
它是**机器可识别、可整体替换的区间**：用标记注释圈定框架块，提取 SLOT 内容 →
换入新骨架 → 回填 → 重跑双闸 + hash。这是存量资产保值的关键基建，且实现成本不高
（框架区边界本来就是确定的）。

#### I-2【高危】content-hash 的 canonical 规则双实现"逐字一致"是定时炸弹

AGENTS.md 自己承认：editor.html 的保存重算与 extract-manifest.py 的 CANONICAL_JS
"逐字一致，改动必须两端同步"。靠人肉同步两份不同语言宿主里的字符串是最经典的
漂移源。

**建议**：把 canonical JS 提成单一 `.js` 文件，extract-manifest.py 在运行时读取
注入 Playwright，editor.html 在 sync-themes.mjs 同款"单源生成"流程里内联进去
（项目已经有这个基建范式）；harness 加一条"两端对同一 fixture 算出同一 hash"的
字节级断言。

#### I-3【中】editor.html 7943 行单文件已过维护临界点

"单文件零依赖"是**交付**约束，不是**开发**约束。425KB 单文件里混着 29 主题的
JSON 数据、三态工作台、Bridge 客户端、脑暴页。建议开发侧拆模块 + 构建期拼接单文件
（sync-themes.mjs 已经证明"生成单文件"的管线可行），交付物不变。否则每次改动的
回归半径都是全文件。

#### I-4【中】结构编辑（undo/页删除/块删除）设计已评审但未落地

`docs/design/editor-structural-editing.md` 的结论正确（"AI 负责构图，人负责删减、
纠错和替换"，P0 = 页级删除/复制/隐藏 + undo）。但当前编辑器**连 Ctrl+Z 都没有**——
就地编辑一个字打错了只能手动改回。对"可以直接编辑"作为头号卖点的产品，无 undo
是用户第一分钟就会撞上的墙。这应该是编辑器侧的最高优先级。

#### I-5【低】run_e2e 856 秒、61 项串行

开发迭代的反馈环太长，建议按子系统分组支持 `--only bridge|themes|export` 并行化，
否则会出现"懒得跑全量"的纪律滑坡。

## 三、主题风格系统

### 做对的

- **七层表达力栈 + 两两 diff≥3 的入库门槛 + 校验器强制执行**，把"主题 ≠ 配色方案"
  从口号变成了机器可验证的 Schema——全行业独一份。
- "世界参考 / unforgettable / 分化声明"三个 G0 必填字段是极好的策展纪律
  （"答不上 unforgettable 就不立项"）。
- 面积-彩度反比律、主客配比律、accent 预算制，这些是真实的平面设计原理落到了
  token 规则上。
- `theme-essence-rebuild` 的十条视觉红线（禁倾斜信息容器、禁弥散投影、大色面
  字重 ≥600）证明主题体系有自我纠错能力。

### 问题

#### T-1【中】主题质量方差大，且没有感知级验收

目前验收全是**几何/结构门禁**（溢出、重叠、字号、色块像素数），没有任何
"好不好看"的验收。progress 文档显示已经发生过整批主题重建（E1/E4/G5/E6/G1/G2/G4
两轮本质重建、G3 被删、README 移除四个"效果欠佳主题"）——说明入库门槛挡不住
"合规但丑"。

**建议**：建立**感知评审闸**——每主题 proving deck 截图过一遍 VLM rubric（项目
已有 bake rubric 六维的基建，复用模式即可），维度：层级清晰度/视觉重量平衡/
装置可辨识度/AI-slop 嫌疑。不作硬门禁（审美裁判权在人），但作为入库 checklist
和回归时的漂移报警。

#### T-2【中】bake_brief（风格圣经）覆盖率约 5/29

AGENTS.md 承认"其余主题铺量中"。这意味着 24 个主题的烙入走"散文 + token 回退"
路径——烙入质量在主题间是两个世代。烙入是 README 主打卖点，应把 bake_brief 铺量
列为 P1。

#### T-3【低】主题数量文档与实际不一致

AGENTS.md/README 说 29 主题，themes/index.md 表格合计 28，sampler 目录 28 张
（G3 已删）。小事，但"文档与实际架构同步"是项目自己的红线。

#### T-4【结构性】主题体系 100% 中文语境

typography.md 的字数预算按全角折算、标题分档按中文字数、主题名/气质描述全中文——
出海时整个 L2 层（字排性格）要重做西文版本。见 §七 G-1。

## 四、HTML→PPTX 工程化

### 做对的

- **双轨并行、单轨失败不互阻、门禁阻断双轨同撤**——产品语义精确（"烙入坏版式到
  哪条轨都是坏的"）。
- **可编辑轨的数学认证闭环**（写入 → 重开 XML → 纯计算认证 R1–R4c → 修复环 →
  修不净页级降级 svgBlip 并逐页列明）比 ppt-master 等竞品的"导出即祈祷"高一个
  代差；wrap=none 单行 + 候选字体集最坏值 ×1.08 + 混排边界 0.25em 实测值，这些是
  真的做过受控实验的。
- **保真轨的坑位台账**（pdftocairo 不带页码叠印、background-clip:text 不可转曲、
  SVG 固有尺寸居中留白）说明每个参数都是实测固化。
- **单向纪律**（导出全程 index.html 只读 + 前后 sha256 比对）、postflight 重开包
  校验、诚实降级链——工程卫生满分。

### 问题

#### E-1【最高危】真实 Office 365 / WPS 目检至今 NOT_RUN

整条可编辑轨的价值主张是"发给 Office/WPS 上的人接着改"，而验收裁判只有
LibreOffice（文档自己承认"只作参考渲染，非裁判"）。数学认证保证的是**自洽**
（按候选字体度量不溢出），不保证**真实渲染器行为**——PowerPoint 的东亚换行规则
（kinsoku）、WPS 的行距实现、365 云端字体回退，每一个都可能让数学模型失效。
这是全项目**最大的一块未验证假设**，且它恰好压在主交付物上。

**建议**：这不是"遗留人工项"，是 P0。最低成本路径：Windows 云虚拟机 + PowerPoint
+ pywin32 导出逐页截图 → 与 export/native/page-NN.png 做 diff，把"真实 Office
渲染 diff"纳入 CI（哪怕每周跑一次）。WPS 同理。在此之前，README 的
"editable version (text and charts are native in PowerPoint)"宣传应加诚实边界注。

#### E-2【中】导出的 PPTX 缺少"PPT 生态公民"属性

目前导出是绝对定位的文本框/形状海——视觉对，但对方拿到后：没有 slide master/
layout（新增一页无版式可套）、颜色没映射到 pptx theme palette（换品牌色无法一键）、
没有 speaker notes。这决定了"对方接着改"的体验上限是"改字"而不是"接着做"。

**建议**（按性价比排序）：

1. 把主题六色 token 写进 pptx 的 `theme1.xml` 配色方案并让元素引用 scheme color
   而非硬 RGB——换色能力立刻解锁，且实现量可控；
2. notes slide 承接每页"这一页的一句话"（页计划表里本来就有这个数据，目前被
   白白扔掉）；
3. master/layout 生成放长线。

#### E-3【低】L3 原生 chart 的覆盖率与失败率没有公开数字

"双源校验容差 5%，不过烙图兜底"——兜底率多高？如果大部分图表都兜底成了图片，
"charts are native"的宣传需要校准。建议 manifest 的 tracks.editable 增加
chart_native_ratio 指标并在验收台账可见。

#### E-4【低】字体合规

"OFL 字体迁移待批"挂了很久。fsType 许可闸做得对，但分发层面（deck 带
fonts/*.woff2 走网页分发）的许可审计应该在开源爆火**之前**完成，而不是之后被
issue 轰炸。

## 五、HTML→Image（烙入/插画）工程化

### 做对的

- **imagegen-adapter 的安全纪律**是教科书级：shell=False 单次启动、magic/尺寸/SHA
  校验后原子发布、staging 目录、basename 白名单、ledger 不落 prompt 正文与凭证、
  不自动重试防重复计费。
- **烙入语义的演进**（保真封存 → 升维，参考图六字诀"只内容与配色"）有完整的实验
  证据链（D 组目检裁决、905 字符截断实测、数据图表三线失真实证 → 定量图表页禁
  烙入）。这种"用受控实验推翻自己上一版设计"的循环是项目最健康的部分。
- 诚实回退纪律（失败槽位保持 placeholder 并逐条列出，"回退不是失败，冒充才是"）。
- check-image-harmony 的 CIEDE2000 色彩一致性后置校验 + 50% 双触发阻断的口径
  设计合理。

### 问题

#### B-1【高】真实付费生图端到端至今 UNKNOWN

验收台账明确：harness bug 已修但未再次付费调用。整条 imagegen v2 管线
（adapter → rubric → harmony → 契约改造）的真实世界表现是未验证的。demos/ 下的
产物是历史跑出来的，不等于当前代码路径验证过。

**建议**：申请一次小额预算跑通 3 页代表场景（封面巨字/数据英雄/图文证据）并把
证据落台账——这比再写一个主题的优先级高。

#### B-2【中】成本治理只有 ledger 没有预算

ledger 记账但没有**预算闸**：一个 20 页 deck 全烙入 + 代表页 `--n 2` + 重 roll
2–3 次，费用上界是多少？用户在哪里看到预估？

**建议**：bake-plan 编译时输出成本预估（页数 × 候选数 × 单价挡位），Bridge intent
回执里带上，超过阈值要求页面二次确认。爆火场景下"不知不觉烧了 $50"是口碑杀手。

#### B-3【中】文字渲染失败是结构性风险，当前只有"事后验收重 roll"

rubric 一票否决 + 2–3 次重 roll 是止损不是治本。两个可做的方向：

1. 前文 P-3 的背景升维混合态——文字根本不进生图，风险归零；
2. 对标题类短文本，生成"无文字版"后用 HTML/SVG 排版合成文字层再整体栅格化
   （即"图表区留空后置合成"思路推广到文字）——bake-prompts.md §0 规则 3 已经为
   图表开了这个口子，文字同理。

#### B-4【低】烙入分辨率 2560×1440 的上限

在 4K 投影/印刷场景会露怯，provider 支持时应升 3840×2160（G7 下限条款已有分辨率
意识，只差把上限也提上去）。

## 六、MCP Bridge / Agent Harness 对接

### 做对的

- **协议设计的概念切分**（A 类事实 vs B 类请求 vs 用户草稿；接收确认/处理权属/
  发布安全三问分离）是整个 bridge 的灵魂，这个切分是对的且罕见。
- attempt 隔离 + revision CAS + rebuild/resume 双恢复语义 + Git 专用 refs 不碰
  用户 HEAD——"架构上消灭 AI 弄坏文件"是真的。
- 五工具极简面（open/await/push/status/close）而不是把 20 个操作都暴露成工具，
  符合 MCP 工具数量与模型调用准确率的反比规律。
- bridge_mcp.py 薄代理 + daemon 不依赖 mcp 包的分层干净。

### 问题

#### M-1【高】Harness 兼容矩阵是当前最大的落地瓶颈

现状：Kimi formal FAIL（observation-07 宿主不退出）、Codex BLOCKED、Claude Code
未见正式验收记录、Kimi 需要手工改 toolTimeoutMs。更深层的问题是
**`await_intent(timeout_sec=86400)` 这个设计把所有宿主的工具超时策略都变成了
兼容性雷区**——60 秒超时（Kimi 默认）、progress 不续命、不同宿主对长挂起工具
调用的处理（心跳、重连、UI 表现）各不相同。一天级的阻塞工具调用在 MCP 生态里是
非常规用法，每接一个新宿主都要重新踩一遍。

**建议**：

- 增加一个**轮询模式档位**作为兼容回退：`await_intent(timeout_sec=30)` 短轮询 +
  SKILL.md 允许"timeout 后结束回合，用户下次说话时 get_status 先查 pending"——
  协议已经支持有界等待，缺的只是技能侧对低超时宿主的正式剧本。
- observation-07 大概率是 stdio server 的 stdin EOF/信号处理问题，应在
  bridge_mcp.py 侧加 stdin 关闭即自退的防御，而不是等宿主修。

#### M-2【中】"恰好五个工具可见"的触发条件脆弱

SKILL.md 的 editor-first 以"恰好五个 pptx-html-bridge 工具可见"为开关。宿主给
工具名加前缀（常见：`mcp__pptx-html-bridge__open_editor`）、用户同时装了别的
MCP server、未来 bridge 加第六个工具——任何一种都会让"恰好五个"的字面判断失效
或歧义。建议改为"`pptx-html-bridge` 命名空间下五个指定名字的工具均可见"的语义
判断，并在 SKILL.md 给出前缀变体示例。

#### M-3【中】loopback-only 限制了半壁江山的使用场景

Bridge 是 127.0.0.1 + 本地浏览器弹窗。而 2026 年大量 agent 跑在远程沙箱/容器/CI
里——`open_browser=true` 在 headless 环境静默无效，用户永远看不到编辑器。协议层
其实只差"可达 URL"这一件事。

**建议**：daemon 支持 `--bind` + 显式 tunnel 文档（或与 serve.json 配套输出一个
可转发端口的说明），并在 open_editor 返回里诚实声明 page_online 探测结果，让
agent 能告知用户"编辑器已启动但本环境无法自动打开，URL 是…"（部分已有
page_online 字段，把剧本补全）。

#### M-4【低】bridge_core.py 2156 行 stdlib 单文件

与 editor.html 同样的单体问题。25 路由 + 7 类 SSE + SQLite 状态机 + Git 保护 +
SecureRoot 全在一个文件里，core 34 项测试覆盖了行为但没降低认知负担。至少按
SecureRoot / 状态机 / HTTP 层拆成三个模块（daemon 仍单进程，不违反零依赖）。

## 七、距离"爆火、效果无敌"还缺的布局（按优先级）

### G-0｜P0：补齐"最后一公里"的真实验证

E-1（Office/WPS）、B-1（真实生图）、M-1（harness 矩阵）三件事共同构成一个事实：
**项目的三个对外承诺（PPTX 可编辑交付、烙入升维、任意 agent 即插即用）都停在
"自动化自洽"而未经真实世界验证**。爆火产品的死法通常不是功能少，而是首批尝鲜者
撞上"README 说能做但实际不行"。这三件事应冻结新特性优先完成。

### G-1｜P0：英文化/国际化

技能、主题、briefing、编辑器 UI 全中文。GitHub 上爆火的 skill 90% 流量来自英文
世界。要做的不只是翻译：

- SKILL.md / references 出英文镜像（机器可从中文单源生成，但要人审）；
- typography.md 增加西文分支（字数预算改字符/词预算、标题分档按 em、
  禁 letter-spacing 条款反转——西文大写标题恰恰需要 tracking）；
- 主题 L2 层补西文字体栈立场；编辑器 UI 做 i18n（单文件内嵌字典即可）。

工作量大但纯执行，建议作为一个独立 iteration。

### G-2｜P0：上手摩擦降到一条命令

现状安装流程：clone → cp skills → pip mcp → claude mcp add 绝对路径 →
playwright install → poppler。每一步都在漏斗上砍人。目标形态：

```bash
uvx pptx-html-bridge init   # 或 npx
```

自动完成 skill 安装、MCP 注册（探测 Claude Code/Codex/Kimi 配置文件）、依赖检查
与按需安装、跑一个 30 秒自检 deck。再配一个 60 秒的 README 顶部视频（现有 GIF
很好但缺"从一句话到成品"的完整叙事）。

### G-3｜P1：编辑器补齐 undo + 页级结构操作

见 I-4。`editor-structural-editing.md` 的 M1''（页删除/复制/隐藏 + 页范围 undo）
设计已评审，直接落地。这是"可以直接编辑"卖点的诚意底线。

### G-4｜P1：演示模式（presenter experience）

目前形态是"16:9 竖向滚动网页阅读"。但 PPT 的高频场景是**讲**：

- 全屏单页演示模式（骨架已有键盘翻页，差一个 presentation mode 切换）；
- 演讲者视图（计时 + 下页预览 + notes）；
- speaker notes 字段——页计划表的"这一页的一句话"天然就是 notes 的种子
  （与 E-2② 同一份数据三处复用）。

缺这块，产品在"发布会/路演"这些 briefing 自己枚举的场景里只完成了一半。

### G-5｜P1：品牌适配层（Brand Adapter）

解 P-2 的矛盾、不破"只选不改"红线的方案：把"企业 VI → 合规主题变体"做成
**受控生成管线**而不是放开自由改色——

输入品牌色/logo/字体 → 自动做面积-彩度反比律与对比度检查 → 在最近邻重主题上生成
一个**合规变体**（变体本来就只许覆盖 G1 六色 ± G3，Schema 完全兼容）→ 过与入库
变体同款的校验器。

审美保护机制全保留，企业刚需得到满足。这是商业化价值最大的单项。

### G-6｜P1：公开 benchmark

项目内部有 61 项回归、容量门禁、保真分，但对外没有任何"比别人好多少"的证据。
建议做一个公开 eval：同一组 brief（10 个真实场景）× 本项目 vs gamma/tome/裸
Claude artifacts，发布渲染结果 + 溢出率/编辑可用性/导出保真分对照。"效果无敌好"
需要被看见，策展过的对比图集就是最好的传播物料。theme-sampler 一 deck × 12 主题
的展示思路已经证明了这条路。

### G-7｜P2：数据接入与图表编辑闭环

charts.md v2 的 14 配方很强，但两个断口：

1. 输入侧没有 CSV/Excel → 图表的直通（briefing 维度池可加"数据文件"入口，转换
   规则确定性强，适合脚本化）；
2. 编辑侧"改数走 AI 流程"的契约断层——用户改一个柱状图数字要发起一轮 agent 任务，
   体验断崖。中期方案：图表几何用 CSS 变量驱动（charts.md 本来就是 `--v/--max`
   思路），编辑器对数值直标提供"改数 → 同步改对应 CSS 变量"的白名单通道，契约加
   一个 `data-chart-value-var` 绑定标记即可，不破"几何 skip"红线。

### G-8｜P2：社区主题管道

七层 Schema + 两两 diff 校验器 + sync-themes 单源管线——**接受社区主题投稿的全部
基建已经存在**，只差一份 CONTRIBUTING-THEME.md（Schema 教程 + proving deck 要求 +
感知评审流程）。主题数量是这类产品的网络效应来源，29 个自产主题撑不起"每个用户
都找到自己的风格"。

### G-9｜P2：竖版/方版画幅

16:9 定死写进了骨架、check-render、导出换算常数。但社媒场景（小红书 3:4、Story
9:16）是 AI slides 增量最大的市场。画幅参数化改造半径大（典型常数 1920×1080/EMU/
PDF 尺寸散落多处），建议先把常数收敛到单一配置源，为未来留门，不急于实现。

## 结语

这个项目的工程底座（三形态架构、双闸同数学、Bridge 一致性、主题 Schema 化）已经
是 SOTA 水平，**它不缺"再深一层的正确性"，缺的是把已有正确性兑换成外部世界可感知
的价值**：真实 Office 里打得开、英文用户看得懂、一条命令装得上、编辑器里有
Ctrl+Z、品牌色进得来、对比图摆得出。

如果只能做三件事：

1. **真实验证三连**（Office/WPS + 付费生图 + harness 矩阵）；
2. **英文化 + 一键安装**；
3. **undo + 背景升维混合态**。

做完这三件，"爆火"所需的产品面才算和它的工程面站到了同一高度。
