# 编辑器结构编辑能力调研：块移动 / 删除 / 更多

> 日期：2026-10-13。范围：`editor.html` v3.7、`skills/html-pptx/`（骨架 v7.6 + 契约 v8.1）、`tools/bridge_core.py`、`tests/harness/`。
> 问题：编辑器当前只支持文字就地编辑、四属性样式、图片替换、批注、整页排序。若在 HTML 层增加**文本框移动/删除、色块移动/删除、图片移动/删除**，是否可行、难度多高、还有什么值得一并考虑？

---

## 1. 现状：编辑器与底层 HTML 各自提供什么

### 1.1 编辑器现有能力（editor.html v3.7，7455 行单文件）

| 能力 | 实现要点 | 位置 |
|---|---|---|
| 就地文字编辑 | 两段手势（首击选中 → 二击进入），`contenteditable='plaintext-only'`，提交时 `\n` 归一化为 `<br>` | `editor.html:3979-4095` |
| 文字样式白名单 | 仅 font-family / font-size / color / text-align，写 inline style，色板写 `var()` 引用 | `:5628-5761` |
| 图片替换 | Bridge 态 POST `/api/bridge/asset`（CAS），FSAA 态写 assets/ 同名覆盖，置 `data-image-state="uploaded"` | `:4583-4649` |
| 批注 | 框选 marquee → slide/path/excerpt 三层引用 → 导出指令，**不进保存产物** | `:4260-4574` |
| 整页排序 | 目录侧栏 HTML5 DnD，drop 时 `deck.insertBefore()` 重排 `.slide-slot` | `:5913-5954` |
| 生图入口 | 重烙当前页 / 补齐插画，Bridge/嵌入/裸静态三态分流 | `:7159-7203` |
| 烙入源层编辑 | `.baked-source` 展开为覆盖层，层内走既有手势 | `:6200-6215` |

**关键事实：当前没有任何移动元素、删除元素、页内布局调整的代码或遗留痕迹。** 唯一改变 DOM 结构的运行时操作是整页排序（粒度是页，不是页内元素）。选中模型的粒度严格限于 `[data-editable]`/`[data-editable-image]` **叶子元素**，没有容器/块级选中概念。

### 1.2 底层 HTML 为可编辑性提供的能力

**(a) 契约标记体系（editing-contract.md v8.1）**

- `data-slide-id`：页级稳定语义 ID；`data-editable`：叶子文本元素（禁止标在容器上）；`data-editable-image` + 图片槽位三属性（slot/intent/state）；`data-editable-skip`：装饰豁免；`data-render-mode` + `.baked-source`：烙入双层结构。
- 兜底寻址：`data-slide-id` + 祖先 child-index 路径（如 `metrics:div.2>span.1`）——批注已用它做跨会话重定位，**移动/删除的目标寻址可直接复用**。
- **契约明文把结构变更划给 AI**：mask-lines 增删行、信息图增删 Item 均标注"编辑器不支持，走 AI 流程"（`editing-contract.md:59,104`）。上线删块 = 修契约。

**(b) 骨架布局模型（skeleton.html v7.6）——最重要的结构性事实**

每页是一个 **1920×1080 固定画布**：`section.slide` 为 `position:relative; overflow:hidden; transform:scale(var(--slide-scale))`（`skeleton.html:86-97`）。这意味着：

- 页内是一个**绝对定位上下文**，拖动写 `left/top` px 值天然落在画布坐标系；check-render / check-capacity 也都按画布坐标量几何。
- 真实产物已大量混用绝对定位：`tests/decks/cmb-retail/index.html` 有 118 处 `position:absolute`（封面主结构即 absolute + inline left/top/width/height），但 **477 处 flex/grid**——正文页主体是流式排布。
- **容器没有 class/标记约定**。check-capacity 靠启发式认容器（有背景色/边框/圆角即容器，`check-capacity.py:71-84`）。"一个色块"在 DOM 里没有显式身份，这是色块移动/删除的核心前置缺口。

**(c) content-hash 与几何解耦（extract-manifest.py:44-70）**

canonical 串只含：slide-id + render-mode + 每个 `[data-editable]` 的规范化文本 + 每个图片的 `slot|intent|state|src`。**位置、尺寸、样式、left/top 全部不进 hash**。推论：

- 移动块（不改 DOM 顺序）= hash 免疫，不触发烙入 stale / 导出重导。**拖动在 hash 层面是免费操作**。
- 删除含 `data-editable` 的内容 → T: 行消失 → hash 翻转 → stale 如实反映"内容变了"——这正是三形态地基想要的语义。
- 移动若改变页内可编辑元素的**文档序**（如流式容器内重排），hash 翻转，属正常重算。

**(d) 运行时净化通道**

编辑器加载即 `__pptxMotion.freeze()` 冻结 ptr/scroll/fx/rotate；`restore(el)` 可把拆字/打字机中途的元素还原纯文本；保存前 `serializeClean()` 摘除全部运行时残留（`--i`、`--mx` 等 CSS 变量、`.in-view`、canvas 尺寸、`?v=` 等，`editor.html:4683-4796`）。**拖动/删除发生在一个已可归到纯净态的 DOM 上**，且 `data-editor-injected` 约定（注入的辅助 UI 不进产物）已为拖拽手柄、吸附参考线等新 UI 预留了通行规则。

**(e) 保存链路对结构改动天然兼容**

所有保存通道传输的都是 `serializeClean()` 产出的**完整 HTML 文本**（非 diff）。Bridge `_publish` 只做 CAS + 快照 + journal + git ref，对 HTML **无结构校验**（唯一内容检查是 SVG 消毒与外链扫描，均不针对结构）。整页拖拽排序（v3.1 起）就是结构性改动走同一路径落盘的先例。**移动/删除块不需要动 bridge_core、edit.py 或嵌入协议。**

## 2. 逐项可行性评估

### 2.1 移动文本框 / 移动图片 / 移动色块（同一机制，合并讨论)

**结论：分两种情况，难度天差地别。**

**情况 A：元素已是 absolute 定位 —— 难度低（约 1–2 周含测试）**

封面、裂屏对开、图文证据谱系的主流结构本来就是 absolute + inline left/top。此时"拖动 = 改两个 inline 数值"，与现有四属性白名单的就地补丁模型完全同构：

- 画布坐标系现成；拖动向量除以 `--slide-scale` 即得画布坐标增量。
- hash 免疫，烙入/导出链路无感。
- 净化与 T1 往返幂等天然兼容（inline style 是产物内容，原样序列化）。
- 交互层可复用批注 marquee 的 iframe 事件路由经验；吸附参考线、拖拽手柄走 `data-editor-injected`。

需要的契约修订：样式白名单新增 `position/left/top`（明确"移动落码为 inline"），AI 落码"保留用户 inline 样式"义务同步扩展（`editing-contract.md:142-143`）。

**情况 B：元素在 flex/grid 流内 —— 难度高，且没有无损 DOM 表达**

正文页主体是流式布局。对万式元素"拖到任意位置"只有三条路，每条都有硬伤：

1. **转 absolute**（按当前渲染 rect 固化为 left/top/width）：元素脱流 → 兄弟回流填补 → 版式塌缩/重叠，且后续文字变长时不再自适应。需要对"善后"做大量设计（是否连带锁定兄弟？是否提示用户？）。
2. **容器内重排**（改 DOM 顺序）：只支持"换序"不支持"自由摆放"；改变 `data-editable` 文档序会翻 hash（语义上可接受）；`--i` 阶梯序号按文档序分配，入场次序静默变化。
3. **margin 偏移**：语义怪异、与对齐工具链不兼容，不建议。

务实路线：**先只支持情况 A + 显式"脱流"操作**（用户明确选择"转为自由定位"，编辑器固化 rect 并提示回流风险），把情况 B 的自由移动降级为"容器内换序"。

### 2.2 删除文本框 / 删除色块 / 删除图片 —— 难度中

技术上是一次 `removeChild()`，难点全在边界与善后：

| 风险 | 说明 | 对策 |
|---|---|---|
| 契约红线 | 结构变更当前明文划给 AI | 契约升 v8.2，定义"可删除元素"白名单 |
| 断言破坏 | compare 族 `data-ig-item` 必须恰好 2/4；删 `.nav-link`/`data-chapter` 断章节跳转；删 `page-baked` img 破烙入三要素 | 删除守卫清单：命中禁删元素时拒绝并解释 |
| 无后悔药 | 当前编辑器**没有 undo/redo**（文字编辑靠 contenteditable 原生栈） | 删除必须先于或伴随 undo 框架上线，否则误删即丢内容 |
| hash 翻转 | 删除含可编辑内容的块 → 相关页 hash 变 → 烙入 stale、导出需重跑 | 语义正确，但 UI 要明示后果（"该页已烙入，删除后需重烙"） |
| 几何失验 | 删除后剩余元素位置不变，一般不会新产生溢出/重叠；但删图片槽位可能留下空容器 | 删除后跑一次轻量几何复检（见 §4.3） |

**图片删除建议改为"重置为占位"**：`data-image-state` 状态机已有 `placeholder → generated → uploaded`（`editing-contract.md:117-128`），删除 img 不如把槽位重置回 placeholder（换回占位图文件 + state 置回），既保住三方绑定校验，又给生图入口留了回补路径。真正的"连槽位一起删"作为二级操作。

### 2.3 色块的特殊问题：身份识别

文本框有 `data-editable`、图片有 `data-editable-image`，**色块什么标记都没有**。要让用户点选"一个色块"，两个方案：

1. **启发式**（零契约成本）：复用 check-capacity 的 isContainer 判定（有背景色/边框/圆角），编辑器 hover 时实时计算候选块。缺点：嵌套容器层级歧义（点的是卡片还是卡片里的色条？）、装饰元素与信息容器混排时误判。
2. **新增块级标记**（契约成本，一劳永逸）：生成侧给容器级元素加 `data-block`（可带角色：`data-block="card|panel|band"`），编辑器只认标记。与 `data-ig`/`data-ig-item` 的既有先例一致。缺点：存量 deck 无标记需回刷，生成侧 SKILL/模板要同步。

推荐**双轨**：有 `data-block` 认标记，没有则回落启发式 + 层级循环选择（重复点击在同位置循环穿过嵌套层，类似设计工具的 deep-select）。

| 功能 | 前置依赖 | 技术难度 | 契约/链路改动 | 综合评级 |

## 3. 横切基础设施：不论做哪项都绕不开的三件事

### 3.1 块级选中模型（一切的前提）

当前选中粒度只有可编辑叶子。需要引入第二级选中——"块"：

- 手势分层：首击叶子（现状），再次点击或 Esc/点击空白升格到最近块级祖先？或者修饰键（Alt+点击）直选块。需要与两段手势、批注 marquee 的事件路由（`editor.html:4100-4146` 一律 `mode!=='edit'` 早退）协调，建议块操作单独一个子模式或修饰键，避免误触。
- 选中态视觉：复用 `.ed-selected` 注入样式体系（INJECTED_CSS `data-editor-injected`）。
- 寻址持久化：沿用 slide-id + child-index 路径（批注已验证跨会话可靠）；DOM 结构变化后路径失效的兜底（matched/changed/missing 三态）也是现成的。

### 3.2 Undo/Redo 框架（删除的硬前置，拖动的体验放大器)

当前编辑器无任何撤销栈。结构操作一旦上线，误删/误拖的代价远高于打错字，**没有 undo 的删除功能不应交付**。

可行方案：命令栈模式——每个结构操作记录为 `{type, targetPath, before, after}`（move 记前后 left/top；delete 记被删子树 outerHTML + 父路径 + 前驱路径），undo 逆放、redo 重放。DOM 级快照太重，命令逆操作足够且与寻址体系自洽。栈上限 50 步，保存后不清空但跨保存提示。工作量中等（约 3–5 天），但它同时惠及文字编辑（把 commitEdit 也接进栈，统一 Ctrl+Z 体验）。

### 3.3 编辑器侧轻量几何复检

生成侧双闸（check-render 溢出 ±2px / 重叠 >16px²；check-capacity 净距 4px）在编辑器保存链路上**不存在**——编辑器可以存出一份过不了 Step 5 的 deck。移动/缩放上线后这个缺口会被真正踩到。

方案：把 check-render 的核心数学（包围盒换算、重叠面积、画布越界）用 JS 重写为编辑器内的 `geometryLint(page)`，移动/缩放/删除结束时跑当前页，违规时在块边缘画警告色（不阻断保存，只提示）。check-render 本体是渲染后量测，JS 版用 `getBoundingClientRect` 换算即可，数学可逐条对齐。这是"编辑器不管几何"到"编辑器守护几何"的定位升级，建议与移动功能同批交付。

## 4. 用户未提及但值得一并考虑的能力

按价值/成本比排序：

1. **方向键微调 + 吸附对齐参考线**（★ 最高性价比）：没有吸附的自由拖动在 PPT 场景几乎不可用——用户真正要的是"对齐"。参考线计算（候选块边缘/中心两两对齐 + 画布中线）是纯几何，配合 `data-editor-injected` 画线，做完拖动功能的 30% 增量换取 80% 的可用性。
2. **Undo/Redo**（§3.2，删除的硬前置）。
3. **删除/复制整页**：目录侧栏已有拖拽排序，加删除（Del 键 + 确认）与复制（duplicate slide-slot + slide-id 加后缀）是自然延伸，成本极低，价值高（做 deck 最常见的结构操作就是页级增删）。
4. **图片重置为占位**（§2.2）：比删除更符合槽位状态机语义。
5. **块缩放（resize 手柄）**：色块/图片改尺寸是高频诉求；图片需同步重算 slot 宽高声明（三方绑定 5% 容差校验仍在生成侧），文本框缩放要联动字号警告（<18px 现有警告机制可复用）。
6. **z-index 上下层**：absolute 块增多后必然需要；契约白名单加 `z-index`，UI 只需"上移/下移一层"两个命令。
7. **复制块 / 新增文本框**：新增文本框 = 往页内插入一个带 `data-editable` 的 absolute 定位 div——技术上简单，但它是"编辑器从修改工具变成创作工具"的分界线，建议明确放在后期里程碑，先不承诺。
8. **几何 lint**（§3.3）：不是功能但建议同批。
9. **批量操作**（多选块对齐/分布/成组删除）：等单块操作稳定后再说。
10. **流式容器内换序**（§2.1 情况 B 的降级形态）："上移/下移一项"对列表类内容实用且无自由移动的塌缩风险。

**不建议进编辑器的**（维持 AI 落码分工）：配色/主题变更（设计面板意图模式已覆盖）、信息图结构增删（`data-ig-item` 计数断言与族语义绑定，契约红线有理）、mask-lines 行增删、烙入页的图层操作（走源层编辑 + 重烙流程）。

## 5. 建议的分期路线

- **M1（选中与后悔药）**：块级选中模型（`data-block` 标记 + 启发式回落 + 层级循环）、undo/redo 命令栈、契约 v8.2 起草（块标记、白名单扩展、可删除守卫清单、脱流语义）。纯地基，无用户可见功能。
- **M2（移动）**：absolute 块拖动 + 方向键微调 + 吸附参考线 + 几何 lint + 白名单落地。验收对标 T2/T10 模式新增结构编辑端到端测试。
- **M3（删除与页级操作）**：叶级块删除（守卫 + undo）、图片重置为占位、整页删除/复制、烙入 stale 后果提示。
- **M4（尺寸与层级）**：resize 手柄、z-index 调整、流式容器内换序。
- **M5（创作边界，需另行评审）**：复制块、新增文本框、流式元素脱流自由移动。

M1–M3 是"移动/删除"诉求的最小完整闭环，预估 3–5 周（含契约修订、生成侧标记回刷、harness 新测试组）。M4+ 按使用反馈决定。

## 6. 风险与开放问题

1. **存量 deck 的 `data-block` 回刷**：29 个主题 × 配色变体的模板、gallery 61 页、cmb-retail 54 页、theme-proving 64 页都要过一遍标记；可用 check-capacity 的启发式半自动标注 + 人工抽查。
2. **契约 v8.2 的双端同步红线**：canonical 规则若因"新增文本框"等功能调整（例如新元素如何进 hash），`editor.html` 与 `extract-manifest.py` 必须逐字同步（现有注释已明示该纪律）。
3. **`--i` 阶梯序号的静默变化**：容器内换序/删除后动效次序变化，需在文档中明示"结构操作可能影响入场次序"，或在净化/加载时按几何位置（top→left）而非文档序重排 `--i`（改动骨架，另行评估）。
4. **烙入页**：块操作应限定在源层编辑态内，完成后标 stale 走重烙；主态（看到的是一张整图）上不做任何块操作——这条边界要在 UX 上焊死。
5. **嵌入协议无需改动**：结构改动仍走 `pptx-html:save` 完整 HTML，宿主无感；唯一新增可选消息是几何 lint 警告的透出（非必须）。

## 7. 需求反思（2026-10-13 补）：哪些是 PPT 制作者真正需要的

### 7.1 修改动机分层

真实 PPT 制作者（汇报/路演/交付前场景）的修改动机只有六层，频率从高到低：① 纠错（错别字、数字）→ 已覆盖；② **删减**（"太长""这页不要""这块不要"——AI 生成物几乎必然偏多，第一反应是做减法）；③ 替换（换图、换案例）→ 已覆盖；④ 微调（改完文字溢出、对齐差一点）；⑤ 重组（页面增删、顺序）；⑥ 重设计（"这页不好看"→ 本产品的答案是批注 + AI 落码，不是手动）。

### 7.2 自由拖动是 PowerPoint 肌肉记忆，不是本产品的真需求

PPT 里拖动是主交互，因为 PPT 是**手工自由画布**——布局本来就靠拖。本产品 deck 是**系统性栅格生成物**，用户继承的是已协调的版式系统，自由拖动只会破坏它。用户说"想拖动"，真实意图通常是三个具体痛点：改字后溢出想挪开（→ 微调 + 几何 lint 即可）、删后留空洞（→ 删除的善后问题，不是移动问题）、图想换位置（→ 低频）。且自由移动与批注→AI 通道**直接竞争**：布局级"不对"已有更优解；为 5px 微调开放自由排版，等于鼓励用户徒手拆 AI 搭好的系统，与"拒绝平庸"基调矛盾。

### 7.3 "色块"不是用户的操作对象

用户眼里没有色块，只有**内容**。色块是主题的排版装置/视觉语言，没人想"把色块左移一点"；真实诉求是"把这个**内容块**挪一下/删掉"，容器应随内容整体走。`data-block` 标记的价值正在于让操作对象 = 容器+内容整体。独立的"色块移动/删除"判定为**伪需求**。

### 7.4 修正后的真需求排序

**真需求（按优先级）：**

1. **删除（块级 + 页级）**——最高频结构操作；方向是"减"，天然安全（不会把 deck 改丑，只会变干净）；AI 生成物冗余是确定性的
2. **Undo/Redo**——不是功能，是信任地基；无它删除不敢上线
3. **页级增删/复制/隐藏**——做 deck 最常做的结构操作其实是页级的；"隐藏页"（保留但跳过）是 PPT 原生心智，比删除更常用，§4 遗漏
4. **微调 nudge + 吸附**——有限真需求，触发点明确（文字编辑后的几何失衡），小步做
5. **图片重置为占位**——换图逆操作，低频但语义自洽

**伪需求 / 拒绝或无限延后：**

- 色块独立移动/删除 → 操作对象搞错，并入"内容块整体"
- 流式元素自由拖动 → 塌缩风险 + 与 AI 通道竞争，双输
- resize / z-index / 复制块 / 新增文本框 → 构图工具、PowerPoint 创作心智；本产品里"加一块内容"的正确路径是批注/脑暴给 AI——新增内容需匹配主题装置、密度纪律、动效阶梯，手工加入的一定是系统外异物

### 7.5 结论与路线修正

编辑器的用户哲学：**AI 负责构图，人负责删减、纠错和替换**。删除是比移动大一个数量级的真需求，微调是比自由拖动更诚实的形态。§5 路线修正为：

- **M1'**：undo/redo 命令栈 + 契约 v8.2（块标记、可删除守卫清单）
- **M2'**：页级删除/复制/隐藏 + 叶级块删除（守卫 + undo + 空洞善后提示）+ 图片重置为占位
- **M3'**：absolute 块微调（方向键 + 吸附 + 受限拖动）+ 几何 lint
- **不做清单**：色块独立操作、流式自由拖动、resize/z-index/复制块/新增文本框（统一导流到批注/脑暴 → AI 落码）
